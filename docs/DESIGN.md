# Design

Why this repo is shaped the way it is. Three decisions carry most of the weight: how a
GFlowNet loss gets gradients out of a model we do not host, where the flow functions live, and
how the reward is shaped.

## 1. The gradient bridge

Tinker exposes exactly five loss functions:

```python
LossFnType = Literal["cross_entropy", "importance_sampling", "ppo", "cispo", "dro"]
```

None of them is Trajectory Balance, and there is no way to ship a loss to the server. The four
RL losses all reduce to `something × advantages` summed over tokens, which covers policy
gradient but not TB — TB's residual `(log Z + Σ log P_F − log R)²` is a *squared* quantity
whose gradient couples every token in the trajectory through a shared scalar.

The way out is `cross_entropy`. Per the docs, it computes

```python
elementwise_loss = -target_logprobs * weights
loss = elementwise_loss.sum()
```

with `weights` an arbitrary per-token float32 array — **arbitrary, including negative**. So for
any client-side differentiable `C(logprobs)`:

```
∂C/∂θ = Σ_t (∂C/∂logprob_t) · (∂logprob_t/∂θ)
```

and setting `weights_t = -∂C/∂logprob_t` makes the backend's own gradient identical to the one
we want. The loss can be anything — TB, SubTB, DB, VarGrad, something not yet invented — as
long as it is a differentiable function of per-token logprobs.

This is not a trick we invented. It is precisely what the SDK's own `forward_backward_custom`
does internally, with the rule stated in its source:

```python
# Backend CE is L = sum(-logprobs * weights), so to backpropagate a
# client-side custom loss C(logprobs) we must send weights = -dC/dlogprobs.
"weights": -grad,
```
— `tinker/lib/public_interfaces/training_client.py:475`

### Why we reimplement it rather than call it

`forward_backward_custom` is the obvious choice and we deliberately do not use it:

| | `forward_backward_custom` | `flowcode.tinker_backend` |
|---|---|---|
| Blocking | `@sync_only`, calls `.result()` internally | fully async, pipelinable |
| `loss_fn_inputs` | restricted to `{target_tokens, weights}` | unrestricted |
| Cost | ~1.5× FLOPs, up to 3× wall time | the same two calls, overlapped |

The `loss_fn_inputs` restriction is disqualifying on its own: it rejects `advantages` and
`logprobs` keys, so behaviour-policy logprobs cannot ride along with the datum — and off-policy
replay is a headline reason to use GFlowNets at all.

### The two passes

```
forward(data, "cross_entropy")          # weights all zero -> per-token logprobs, no gradient
  ↓
C(logprobs) in torch, C.backward()      # our objective, client side
  ↓
forward_backward(data, "cross_entropy") # weights = -dC/dlogprobs -> correct gradient on the server
```

That first pass is a real cost: it doubles the training tokens per step. It is avoidable when
rollouts are strictly on-policy — sync sampler weights immediately before sampling and the
sampler's returned logprobs *are* the current policy's, so the oracle pass is redundant. That is
`train.on_policy_only`, and it roughly halves the training half of the bill. It is mutually
exclusive with replay, and the trainer raises rather than letting the two coexist: replayed
trajectories were generated by a stale policy, so reusing their stored logprobs as if they were
current would silently corrupt every gradient.

### Alignment

Everything hangs off one contract, asserted on every datum:

```
ob_len        = prompt.length - 1
model_input   = prompt + completion_tokens[:-1]
target_tokens = [0]*ob_len + completion_tokens
weights       = [0.0]*ob_len + <per-completion-token values>
assert model_input.length == len(target_tokens) == len(weights)
```

Position *i* of the input predicts `target_tokens[i]`; prompt positions are zero-padded and
carry zero weight. `TinkerBackend.compute_logprobs` strips that padding before objectives see
anything, and `apply_gradient` re-adds it. **No objective ever handles a padded tensor** — they
receive exactly `(len(completion_tokens),)` and that invariant is what keeps the off-by-one
errors in one file instead of five.

### Normalization

Every Tinker loss ends in `.sum()`, not `.mean()`, and gradients accumulate across
`forward_backward` calls until `optim_step` flushes them. There is no server-side
normalization. We therefore pass an explicit `grad_scale` rather than letting the denominator
be implicit — a batch-size change would otherwise silently rescale the learning rate.

## 2. Where the flows live

TB needs `log Z(x)`. SubTB and DB need `log F(s)` at intermediate states. In the literature both
are extra heads on the language model itself, sharing its representations.

**We cannot do that.** Tinker hosts the model; there is no API to attach a head, and no access
to hidden states. So flows live client-side as our own `torch.nn.Module`s with their own Adam
optimizer at their own learning rate (`train.flow_lr`, typically ~1000× `policy_lr` — they are
fitting a scalar per prompt, not a language model, and at the policy LR they lag so far behind
that the TB residual measures log Z error rather than policy error).

- `ConditionalLogZ` — an embedding table keyed by task id. Exact for a fixed training set, which
  is what we have. This one is *not* an approximation.
- `LogFlowEstimator` — an MLP over the features we actually possess: task embedding, normalized
  position, cumulative logprob, and the partial reward when a state carries one.

`LogFlowEstimator` **is** a real approximation and the honest weak point of the SubTB/DB paths:
it cannot see the prefix, so it cannot in general represent the true `log F`. The convergence
tests isolate this deliberately — they give SubTB and DB a *tabular* flow, which proves the loss
mathematics is right, and test the production estimator separately for finiteness and for
moving the policy in the right direction. Two states with different prefixes and equal features
are indistinguishable to it.

This is the main reason **VarGrad is the default objective**. It estimates `log Z` in-batch as
the group mean of `(β log R − Σ log P_F)` and needs no learned flow at all, sidestepping the
approximation entirely. TB with `ConditionalLogZ` is the next most trustworthy. SubTB and DB
offer denser credit assignment and should be *tested*, not assumed better — that comparison is
the experiment this repo exists to run.

## 3. Reward shaping

GFlowNets learn `p(x) ∝ R(x)`. The reward is not a scalar to be maximized, it *is* the target
distribution — so reward defects corrupt the objective rather than merely adding variance the
way they would in PPO. Two consequences drive the environment design:

**Determinism is mandatory.** Fixed `PYTHONHASHSEED`, sorted test order, no wall-clock or
randomness in scoring. A reward that varies run to run defines a different target every step.

**Partial credit is mandatory.** Tests run individually so `pass_fraction` is graded, not
binary. Under all-or-nothing scoring nearly every early sample sits at the reward floor, every
trajectory in a group gets the same `log R`, and the VarGrad group variance — the entire
learning signal — goes to zero.

`log R = β · log(max(pass_fraction, floor))`. The floor keeps `log R` finite for total failures
(without it, one broken sample poisons a batch with `-inf`). β sharpens the target,
`p(x) ∝ R(x)^β`; large β collapses toward argmax and throws away the diversity that motivates
using GFlowNets in the first place.

## 4. What the sandbox is and is not

`flowcode.envs.sandbox` runs model-generated code in a subprocess with rlimits, a process-group
kill on timeout, a fresh temp cwd, and a scrubbed environment (verified by test: a completion
that prints `os.environ` cannot see `TINKER_API_KEY`).

It is a safety net against **accidents** — infinite loops, memory bombs, fork bombs, print
floods, stray writes. It is **not a security boundary**. Untrusted code can still read anything
the training user can read, write where that user can write, and open sockets. Real isolation
needs a container with a read-only rootfs and no network namespace, gVisor, or seccomp-bpf.
That is out of scope, and named rather than half-simulated.

macOS caveat: `RLIMIT_AS` prevents CPython from starting on Darwin, so it is skipped there and
`MEMORY_LIMIT_SUPPORTED` is `False` — a memory bomb is caught only by the wall clock.

## 5. Trajectory segmentation

A `Trajectory` carries `segments`: contiguous, non-overlapping, covering every completion token.
Segments are where SubTB's and DB's intermediate terms attach, and they are the reason one
implementation serves both granularities:

- `granularity: token` — one boundary per token. The standard LLM-GFlowNet setting, O(T²) pairs.
- `granularity: turn` — one boundary per assistant turn. Matches the agentic framing, few pairs.

The current code-generation environment is single-turn, so turn-level collapses to one segment.
The abstraction is in place for a genuinely multi-turn agentic environment (model issues
read/write/run tool calls, reward from the final test run), which is the natural next step and
the setting where turn-level SubTB should actually pay off. Note that a multi-turn renderer must
have the *sequence extension property* — successive prompts each a prefix of the next — or the
training cost goes O(T²) instead of O(T).

SubTB's O(T²) pairs are vectorized, not looped. Writing `G_k := log F(s_k) − C_k` where `C_k` is
the cumulative `Σ log P_F` at boundary `k`, every pair residual collapses to `G_i − G_j` — one
subtraction on a length-`M+1` vector. `max_pairs` bounds the count by seeded subsampling, always
retaining the `(0, M)` anchor, which is the TB constraint and the only pair pinned to the true
reward.

## Open questions

- Does the `LogFlowEstimator` approximation cost enough to make SubTB lose to VarGrad in
  practice? The convergence suite says the SubTB *loss* is correct; it says nothing about
  whether a featureless flow estimator is good enough on real trajectories.
- Is `prompt_cache_hit_tokens` actually excluded from sampling charges? The cost model assumes
  so; `cost.from_usage` exists to check that against a real invoice.
- Does the diversity advantage survive at scale — i.e. does GFlowNet fine-tuning find more
  distinct passing solutions per task than a PPO baseline at equal spend? That is the
  hypothesis; nothing here has tested it yet.
